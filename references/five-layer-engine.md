# 五层递进法律研究引擎

> legal-research 开源版
> 本文件被 legal-research SKILL.md 引用。进入五层引擎时加载。

## 执行模式路由

**进入引擎后先判断模式**：

```
深度模式（默认，SKILL.md 发文确认后进入）：
  → retrieve_first 策略
  → Phase 检索（L2+L3 全通道并行） → barrier → Phase 分析（L4+L5 全量上下文）

常规模式（用户明确拒绝深度模式时）：
  → interleaved 策略
  → L1 → L2 → L3 顺序执行（边检索边输出）
```

### P0: 视角发现（STORM-inspired · 新增）

**目标**：在进入法律概念拆解之前，先识别与这个法律问题相关的利益相关方视角，生成分视角研究问题。

> 灵感来源：Stanford OVAL Lab STORM (NAACL 2024) —— 多样化视角 → 多样化问题 → 多样化检索结果。
> 详细方法论见 `references/perspective-discovery.md`。

**触发条件**：
- R1 only（简单法条查询）→ 跳过 P0
- 进入五层引擎（常规/深度）→ 执行 P0

**执行步骤**：

```
对用户提出的法律问题：
  ├── Step 1: 识别案件类型（合同/侵权/公司/行政/刑事……）
  ├── Step 2: 从视角模板中选择适用视角（默认 P0-P5，按案件类型增补）
  ├── Step 3: 为每个视角生成 2-3 个定向查询
  │     - 法规查询（→ 注入 L2）
  │     - 案例查询（→ 注入 L3）
  │     - 政策/实务查询（→ 注入 L2/L3 补充）
  ├── Step 4: 标注研究优先级（用户立场 → P1/P2 重点）
  └── Step 5: 输出视角矩阵 → 进入 L1
```

**视角选择规则**：

| 案件类型 | 默认视角 |
|---------|---------|
| 通用 | P0(规范分析) + P1(原告) + P2(被告) + P3(裁判者) + P4(监管) + P5(实务) |
| 合同纠纷 | 通用 + P6(合同起草者) |
| 侵权纠纷 | 通用 + P7(受害人) |
| 公司/商事 | 通用 + P8(小股东) + P9(债权人) |
| 行政诉讼 | P10(行政相对人) + P11(行政机关) + P3(裁判者) + P4(监管) |

**输出格式**（用户可见）：

```markdown
## P0: 研究视角

### 识别到的利益相关方视角

| # | 视角 | 核心关切 | 研究优先级 |
|---|------|---------|-----------|
| P0 | 法律规范分析 | [关切] | 🔴 必选 |
| P1 | [原告角色] | [关切] | 🔴 重点 |
| P2 | [被告角色] | [关切] | 🔴 必选 |
| P3 | 裁判者 | [关切] | 🟠 重要 |
| P4 | 监管 | [关切] | 🟡 参考 |
| P5 | 实务 | [关切] | 🟡 参考 |

### 分视角研究问题

**P1（[原告]）视角**：
1. [定向问题1]
2. [定向问题2]

**P2（[被告]）视角**：
1. [定向问题1]
2. [定向问题2]

**P3（裁判者）视角**：
1. [定向问题1]
2. [定向问题2]
```

**P0 完成后**：展示视角矩阵给用户，询问「视角识别是否准确？需要补充或调整吗？」。用户确认后进入 L1，或说「继续」「没问题」直接跳过确认。

### L1: 概念映射（引擎内部执行）

**目标**：把大白话问题拆成精确法律概念矩阵，标注逻辑依赖关系。

**内部指令**（不对用户展示）：
```
对以下法律问题进行概念拆解：
1. 列出所有涉及的法律概念（精确到法律要件层面）
2. 标注概念间的逻辑关系：前提条件／递进／并列／互斥
3. 标注分析顺序：哪些概念必须先确定，才能分析后续概念
4. 每个概念对应的核心法律要件

输出格式：概念矩阵
```

**输出示例**（用户可见）：
```markdown
## L1: 概念矩阵

**原始问题**：建设工程价款优先受偿权行使期限

| # | 概念 | 逻辑关系 | 依赖 | 法律要件 |
|---|------|---------|------|---------|
| 1 | 优先受偿权主体资格 | 前提条件 | — | 与发包人订立施工合同的承包人 |
| 2 | 行使期限起算点 | 递进 | → #1 确定后方可分析 | 应付工程款之日（建工解释一 §41） |
| 3 | 行使期限长度 | 并列 | → 依赖 #2 确定起算点 | 18个月（建工解释一 §41） |
| 4 | 行使方式 | 递进 | → 依赖 #2+#3 | 协议折价/申请法院拍卖 |
| 5 | 权利冲突 | 互斥 | → 与抵押权、购房消费者权利的顺位 | 民法典 §807 + 建工解释一 §36 |

**分析顺序**：#1→#2→#3→#4→#5
```

**L1 完成后**：展示概念矩阵给用户，询问「概念拆解是否准确？需要调整吗？」。用户确认后进入 L2，或说「继续」「没问题」直接跳过确认。

### 深度模式：retrieve_first 执行流程

**触发条件**：`depth = deep`

```
Phase A: 检索语句确认（OLAW 式 + 可纠正 query）

  L1 概念矩阵确认后 → 生成检索语句：
  ┌──────────────────────────────────────────────┐
  │ 📋 深度检索计划                                │
  │                                              │
  │ 基于概念矩阵，生成以下检索语句：                  │
  │                                              │
  │ 🔍 法律数据库: 逐概念检索法条原文 + 类案检索     │
  │   （按 registry.json 中已接入的源执行）           │
  │                                              │
  │ 🔍 案例效力分级 C→D→E:                          │
  │   "[争议焦点] 指导性案例 / 人民法院案例库"         │
  │   → 未命中退 公报/典型案例 → 再退普通文书         │
  │                                              │
  │ 🔍 本地知识库（如已建库）:                        │
  │   "[概念关键词] [法条名称]"                     │
  │                                              │
  │ 🔍 联网搜索:                                    │
  │   官方法规库 + 权威信源交叉核验                   │
  │                                              │
  │ 预估检索产物: ~15-20K token                     │
  │                                              │
  │ ⚠️ 请检查以上检索语句是否准确：                    │
  │   - 法条名称/编号是否对？                        │
  │   - search_case 的关键词是否覆盖所有争议焦点？     │
  │   - 有无遗漏的检索方向？                         │
  └──────────────────────────────────────────────┘
  
  ⏸️ CHECKPOINT：用户确认检索语句 → spawn Retrieval Agent
     用户纠正 → 修改语句后重新展示（如："第四条"→"第四条 第(三)项"）
     目的：OLAW 模式——在 query 层面纠正，而非只在"搜多少"层面确认

Phase B: 全量检索（spawn 独立 Retrieval Agent，进程级隔离）

  spawn Agent(
    name="retrieval-agent",
    subagent_type="general-purpose",
    prompt="你是独立检索 Agent。你的唯一任务是检索，不做分析、不下判断。
    
    ## 输入
    概念矩阵：[L1 概念矩阵内容]
    检索目标：[用户原始问题]
    案件背景：[如涉及企业/当事人]
    
    ## 检索通道（按 registry.json 中已接入的源全部执行）
    1. 法律数据库（北大法宝/元典等 MCP）:

         不得跳过 C/D 级
    2. 本地知识库（如已建库）:
       - 检索自有案件/文章语料
    3. 联网搜索:
       - 最新政策/法规动态
       - 法答网精选答问补检："法答网精选答问 [争议焦点关键词]"
       - 人民法院案例库 site:rmfyalk.court.gov.cn 补检
    
    ## 输出（纯事实，禁止分析判断）
    写入文件: {workspace}/retrieval-consolidated.md
    
    文件结构：

    ## 法条原文
    | 法条 | 原文 | 来源 | 时效 |
    |------|------|------|------|
    
    ## 类案检索
    | # | 法院 | 案号 | 裁判要点 | 来源 |
    |---|------|------|---------|------|
    
    ## 企业信息（如适用）
    | 企业名 | 诉讼历史 | 司法风险 | 来源 |
    
    ## 政策动态
    | 来源 | 内容摘要 |
    
    ## 约束
    - 不输出任何分析、判断、建议

    - 你做完检索就 shut down，不做其他事"
  )
  
  → Retrieval Agent 输出 retrieval-consolidated.md（原始）

  Phase A.5: 重排 + 压缩🆕
  
  原始检索结果可能 50-100K token，全量加载导致"lost in the middle"
  → rerank：按 L1 概念矩阵相关性排序
  → compress：结构化 schema 提取
    - 法条表: | 法条 | 原文 | 来源 | 时效 |
    - 案例表: | 法院 | 案号 | 裁判要点 | 来源 |
    - 企业表: | 企业 | 诉讼历史 | 司法风险 |
  → 忠实性门控：压缩前后信息完整性比对（丢失>10% → 降级为分批）
  → 输出 retrieval-compressed.md（原始体积 30-50%）

  Phase A.6: 检索充分性评估🆕
  
  检查 L1 概念矩阵的每个概念是否有足够支撑：
    - 每个概念 ≥ model_profile.rag_sufficiency_min.law_per_concept 条法条
    - 每个争议焦点 ≥ model_profile.rag_sufficiency_min.case_per_focus 件案例
    ├─ 充分 → 进入 Phase B
    └─ 不充分 → 追加检索（最多 2 轮），标注 [检索追加 第N轮]
  
  → Retrieval Agent shut down → 上下文销毁
  ─── barrier ───

Phase B: 深度分析（Main Agent，加载压缩后上下文）

  加载 retrieval-compressed.md（压缩后，注意力高效区间）
    ├─ L4 反方论证: 基于压缩后检索材料攻击论点
    └─ L5 盲区扫描: 合伙人视角在精炼知识背景上找遗漏
    → 综合输出: 五层深度研究报告.md
  
  对比：加载原始文件 →：加载压缩后文件，注意力更集中
```

**关键约束**：
- Phase A（检索计划确认）：L1 确认后必须展示检索计划，用户确认后才进入 Phase B——防止错误方向撒网
- Retrieval Agent 进程级隔离——spawn 独立 Agent，上下文不与 Main Agent 共享
- 检索阶段 **不对用户展示**——只告知「正在检索法条/案例/企业信息」
- Retrieval Agent 只输出事实，不输出分析判断
- barrier 检查：`retrieval-consolidated.md` 非空且含 `## 检索结果汇总` 标题 → 进入 Phase B
- Retrieval Agent 完成后 shut down → 上下文销毁 → Main Agent 从文件加载，不受检索过程偏见影响
- 失败处理：Retrieval Agent 超时或 spawn 失败 → Main Agent 降级为文件中介方式，标注 ⚠️「检索 Agent 不可用，Main Agent 自行检索」

### L2: 法规定位（引擎编排 R1 + 体系构建）

**目标**：按 L1 概念矩阵逐概念构建跨层级法规体系，标注各地口径差异。

**执行流程**：
```
对 L1 概念矩阵中的每个概念：
  ├── [🔴 强制 Step 0] 本地 KB 检索（retrieve_first 首选源，如已建库）：
  │     用本地检索工具查询 "[概念关键词] [法条名称] [条款号]"
  │     ├── ✅ 命中 → 直接使用原文，标注来源 [本地KB·已核实] + doc_id
  │     └── ❌ 未命中 → 标注 [本地KB·未命中]
  ├── [🆕 P0 视角注入 Step 1x] 按 P0 生成的视角查询定向检索：
  │     foreach 视角 p in P0输出:
  │       - 法规查询: "[核心法条] [p.立场词] [p.关切词]"
  │       - 政策查询: "[p.关切领域] 最新规定"
  │     标注来源时注明视角: [P1视角·已核实] / [P2视角·已核实]
  ├── [回退 Step 1] 法律数据库检索（北大法宝/元典等 MCP，按 registry 状态启用）
  │     ├── ✅ 命中 → 标注来源 [法律数据库·已核实]
  │     └── ❌ 未命中 → 进入下一步
  ├── [回退 Step 2] 联网搜索（官方法规库 + 权威信源）
  │     ├── ✅ 命中 → 标注来源 [WebSearch·已核实]
  │     └── ❌ 仍未命中 → 输出「未检索到相关法条原文」+ 标注 [CITE NEEDED]
  ├── [🚫 绝对禁止] 任何时候不得凭模型内置知识编造法条
  │     无法从任何来源检索到的 → 不输出具体法条，诚实标注缺失
  ├── 按效力层级组织：法律→行政法规→司法解释→地方纪要
  ├── 标注各地口径差异（如各省高院纪要差异）
  └── 标注规范间的适用关系（特别法优于一般法、新法优于旧法）
```

> **执行指令**：L2 所有法条检索遵循「法条引用规则」的6级来源优先级，详见该章节。Step 0（本地 KB 检索）为强制步骤，本地知识库按 registry 状态动态启用。

**输出格式**：
```markdown
## L2: 法规体系

### 概念 #1: [概念名称]

| 效力层级 | 规范名称 | 条款 | 内容摘要 | 时效 | 来源 |
|---------|---------|------|---------|------|------|
| 法律 | [名称] | 第X条 | [核心内容] | ✅ 现行有效 | [法源] |
| 司法解释 | [名称] | 第X条 | [核心内容] | ✅ 现行有效 | [法源] |

**各地口径差异**：
| 地区 | 规范/纪要 | 口径要点 | 与主流差异 |
|------|---------|---------|-----------|
| 地区A | [来源] | [要点] | [差异说明] |
| 地区B | [来源] | [要点] | [差异说明] |

**适用关系**：[特别法/新法/上位法优先说明]
```

### L3: 裁判预判（引擎编排 R2 + 倾向分析）

**目标**：分析裁判倾向，**不罗列案号**——只分析裁判逻辑和趋势。

**核心原则**：
- 法律告诉你「应该怎样」，案例告诉你「实际怎样」
- 不列案号（如需验证→用案例检索工具获取全文）
- 按法院层级和地域分层分析倾向
- 🆕 案例按**支持哪方视角**标注：P1 支持 → P2 支持 → P3（法院）中立
- 🆕 不同视角的案例分别检索，避免「只搜到支持某一方的案例」

**执行流程**：
```
对 L1 概念矩阵中的每个争议焦点：
  ├── [🆕 P0 视角注入] 按 P0 视角分别检索案例：
  │     - P1（原告视角）查询: "[争议焦点] [支持/确认/赔偿] 判例"
  │     - P2（被告视角）查询: "[争议焦点] [驳回/抗辩/免责] 判例"
  │     - P3（法院视角）查询: "[争议焦点] 指导案例 裁判规则"
  ├── [🔴 强制] 案例效力分级检索（C → D → E 强制顺序，常规模式至少 1 轮 C 级）：
  │     - C 级: 指导性案例 / 人民法院案例库入库案例
  │     - D 级: 公报案例 / 典型案例
  │     - C/D 如实标注「未检索到」后 → 才退 E 级（普通裁判文书）
  │     - 争议焦点拿不准 → 法答网精选答问补检
  ├── 触发 R2 案例检索（复用现有 Round 2 工具链）
  ├── 按法院层级分析：最高法 / 高院 / 中院 分别什么倾向？
  ├── 按地域分析：各省/直辖市口径差异？
  ├── 提取最常考量的因素（法院支持/驳回时的核心考量是什么）
  ├── 🆕 按视角标注：每个裁判倾向主要支持哪方视角的关切
  └── 不列案号，只输出裁判逻辑分析
```

**输出格式**：
```markdown
## L3: 裁判预判

### 争议焦点 #1: [焦点名称]

**整体倾向**：[支持方/反对方/存在分歧]

| 法院层级 | 倾向 | 核心考量因素 | 趋势 |
|---------|------|------------|------|
| 最高法 | [倾向] | [因素1、因素2] | [趋势] |
| 省高院 | [倾向] | [因素1、因素2] | [趋势] |
| 中院 | [倾向] | [因素1、因素2] | [趋势] |

**地域差异**：
| 地区 | 与主流差异 | 实务建议 |
|------|-----------|---------|
| 地区A | [差异] | [建议] |
| 地区B | [差异] | [建议] |

**裁判逻辑摘要**：[法院支持该论点时最常考量的3-5个核心因素]
**薄弱环节**：[法院驳回时最常见的原因]
```

### Q0: 检索追问循环（STORM-inspired · 新增）

**目标**：L2+L3 完成后，基于已有检索结果自动检测薄弱点，生成追问查询并补充检索，弥补单轮检索的视角盲区。

> STORM 论文消融实验证明：去掉多轮对话 → outline recall 从 86.26% 降到 77.97%（-10%）。
> 这说明「看到结果→基于结果追问」的迭代深度，比「一次搜完」有质的差距。
> 
> Q0 就是这个迭代层——不是预设的层间逻辑，而是**基于检索结果动态生成的追问**。

**触发条件**：

| 模式 | Q0 执行强度 | 追问轮数 |
|------|-----------|---------|
| R1 only（简单查法条） | 跳过 | 0 |
| 常规模式（L1→L2→L3） | 轻量追问（仅 P0 关键视角缺口） | 1 轮，≤3 条追问 |
| 深度模式（五层全开） | 全量追问（对照 P0+L1 全矩阵） | 3 轮，每轮 ≤5 条追问 |
| | R1→R2→R3，逐轮收紧缺口。深度模式走最大能力通道，不设早停。 | |

**执行流程**：

```
L2+L3 输出完成
  ↓
【Q0 Step 1: 缺口扫描】
对照以下三个维度，逐项打分（✅ 充分 / 🟡 部分 / 🔴 缺失）：

a. P0 视角覆盖度：
   - P1（原告）视角：检索到的法条/案例是否充分覆盖其关切？
   - P2（被告）视角：是否有独立的抗辩路径检索结果？
   - P3（裁判者）视角：是否有法院口径/指导案例？
   - P4（监管）视角：是否有行政合规信息？
   - P5（实务）视角：是否有执行/实操信息？

b. L1 概念矩阵覆盖度：
   - 每个概念是否都有法规 + 案例双支撑？
   - 概念间的依赖关系是否在检索结果中体现？

c. 检索质量检查：
   - 是否有明显的矛盾结果（如 P1/P2 视角的案例指向相反结论）？
   - 是否有「搜到了但信息量不足」的结果（如只有标题没有内容）？
   - 是否有「应该搜到但完全没搜到」的领域？

d. 案例效力覆盖度：
   - 每个争议焦点是否已尝试 C 级（指导性案例/入库案例）检索？
   - C/D 级缺失是「未命中」（已检索，如实标注）还是「未检索」（跳过）？
     未检索 → 直接生成 C/D 级追问查询，不视为缺口已填
  ↓
【Q0 Step 2: 追问生成】
对每个 🔴 缺失或 🟡 部分的项，生成 1 条追问查询：

追问查询生成规则：
  - 不能和已有检索 query 重复（检查 L2/L3 已执行的查询）
  - 必须比原查询更深一层——不是换个说法，是看原结果后想到的「新问题」
  - 优先转译矛盾——如果 P1 和 P2 的案例结论相左，追问「二者分歧的关键事实差异」
  - 格式："[发现缺口描述] → 追问查询：[具体 query]"

限制：常规模式 ≤3 条追问；深度模式每轮 ≤5 条追问，共 3 轮。后轮追问数量自然递减（缺口逐轮被堵上）。
  ↓
【Q0 Step 3: 补充检索】
逐条执行追问查询：
  ├── 法规类追问 → 走 L2 检索通道（来源优先级同上）
  ├── 案例类追问 → 走 L3 检索通道
  └── 政策/实务追问 → 走 WebSearch

每条追问结果标注 `[追问补充]` 来源前缀。
  ↓
【Q0 Step 4: 结果合并 + 分析修正】
  - 补充检索结果合并到原 L2/L3 输出中
  - 对比补充前后差异：追问结果是否改变了原有结论？
  - 如补充结果与原检索矛盾 → 标注为 [争议待核]，升级到 L4 反方论证环节
  ↓
【Q0 Step 4.5: 轻量自检（Self-RAG ISREL+ISSUP）· 新增】
> 灵感的来源：Self-RAG (ICLR 2024 Oral) — 检索和审查不应先后分离，应交织进行。
> 轻量自检 ≠ L4/L5 对抗审查。前者只管「这轮追问搜到的信息有用吗、可靠吗」，
> 后者管「整个分析报告站得住脚吗」。
> 如果跳过自检让 Q0 三轮盲跑，R1 的方向偏差会污染 R2/R3——Self-RAG 的核心教训。

  对当轮补充检索结果逐条检查：

  a. 相关性检查（ISREL — Information Relevance）：
     - 新搜到的信息是否真的填补了声明的那条缺口？
     ├── ✅ 通过 → 纳入上下文，标注 [追问补充·已验证]
     ├── 🟡 部分相关 → 纳入但标注 [追问补充·部分相关]，限制下游引用
     └── 🔴 不相关 → 不纳入，标注 [追问未命中]，不计入追问效果

  b. 可靠性检查（ISSUP — Information Support）：
     - 新信息的来源层级（法律数据库 > 官网 > 通用搜索 > 无出处）？
     - 是否和已有检索结果明显矛盾？
     ├── ✅ 通过 → 标注来源层级
     ├── 🟡 低层级来源 → 标注 [追问补充·来源待升级]
     └── 🔴 与已有结果矛盾 → 标注 [争议待核]，不进下游，升级到 L4

  自检结果写入追问记录（见下方格式新增的自检列）。
  - ISREL 🔴 或 ISSUP 🔴 的新信息 → 在下一轮追问中不计入「已填补的缺口」
  - ISREL 🔴 → 该缺口在下一轮追问中重新列入待填补项
  ↓
【Q0 Step 5: 追问记录归档】
输出追问记录到研究报告，见下方格式。
  ↓
→ 进入 L4/L5（基于补充后的完整检索上下文）
```

**追问记录输出格式**（追加到研究报告，在 L3 和 L4 之间）：

```markdown

```

**约束**：
- 深度模式 Q0 追问执行 **3 轮**（R1→R2→R3），不再递归。常规模式 1 轮。
- 每轮追问前做缺口扫描——R2 扫描含 R1 补充结果，R3 扫描含 R1+R2 补充结果。
- 🆕 每轮追问后执行**轻量自检**（ISREL 相关性 + ISSUP 可靠性）——检索和审查交织，不让追问盲跑三轮。ISREL 🔴 不纳入下一轮上下文；ISSUP 🔴 不进下游，升级到 L4。
- 追问查询不能和 L2/L3 及前几轮已执行的查询语义重复（检查是否实质性新问题）。
- 追问记录必须保留轮次标注 + 自检结果 + 终止原因——这是研究透明性的证据。

### L4: 反方论证（仅深度模式，调用 quality-gate）

**触发**：五层全开模式。

**执行方式**（两种，按可用性选择）：
```
方式A（推荐）: spawn 独立 Agent 做对抗核验
  1. 合并 L1 概念矩阵 + 全量检索材料 → research-draft.md
  2. spawn 独立 Verifier Agent:
     - 输入: research-draft.md（含全量检索上下文）
     - 核验维度: 对方反驳 + 法律依据 + 薄弱环节 + 诉讼策略预判
     - 要求: Verifier 基于完整检索材料攻击论点，而非仅凭研究报告本身
  3. 根据核验报告修正研究报告

方式B（降级）: 同上下文自检
  标注 ⚠️「对抗核验不可用，以下 L4/L5 为同上下文自检，非独立盲审」
```

**输出（追加到研究报告）**：

### L5: 盲区扫描（仅深度模式，调用 quality-gate 扩展维度）

**触发**：五层全开模式。L4 通过后执行。

**深度模式增强**（retrieve_first）：
- L5 Verifier 输入文件含 `retrieval-consolidated.md` 全量检索结果
- 合伙人视角在完整知识背景上审阅——能在检索材料中发现"明明有相关法条/案例但研究了没提到"的遗漏
- 常规模式：L5 只审研究报告本身 → 深度模式：审研究报告 + 检索材料的交叉比对

**执行**：
```
spawn 独立 Verifier Agent（或同上下文自检，需标注降级）:
  - Verifier 角色：资深合伙人视角
  - 审阅视角：
    a. 有哪些重要问题完全没提到？（程序/实体/策略）
    b. 有哪些论点提到了但论证薄弱？
    c. 程序性遗漏：时效、管辖、送达、保全、执行
    d. 策略性遗漏：调解底线、和解筹码、替代方案
    e. 从对方律师角度，会从哪个没想到的角度切入？
  - 输出：盲区报告
```

**输出（追加到研究报告）**：
```markdown

### 程序性提醒
- 诉讼时效：[状态 + 风险]

- 保全：[是否需要 + 线索]
```
