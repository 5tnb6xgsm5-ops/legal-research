# 视角发现引擎（STORM-inspired Perspective Discovery）

> 被 legal-research SKILL.md 和 five-layer-engine.md 引用。
> 灵感来源：Stanford OVAL Lab STORM (NAACL 2024, arXiv:2402.14207)

## 第一性原理

STORM 论文的核心洞见：**多样化视角 → 多样化问题 → 多样化检索结果**。
两个假设直接适用于法律检索：
1. 不同视角的人问不同的问题（原告律师 vs 被告律师 vs 法官搜的东西完全不同）
2. 深度问题需要迭代式追问才能形成（单轮检索 = 表面信息，多轮追问 = 层层深入）

单一默认角色（「帮我研究XX法律问题」）等价于 STORM 对比实验中的 Direct Prompting
——只能搜到最表层的「What/When/Where」信息。
从不同 stakeholder 角度发问，才能覆盖法律问题的全貌。

## P0 执行时机与条件

| 模式 | 是否执行 P0 | 说明 |
|------|-----------|------|
| R1 only（简单法条查询） | 跳过 | 不浪费 token |
| 常规模式（L1→L2→L3） | 执行 | 5-6 视角，每个视角 2-3 查询 |
| 深度模式（五层全开） | 执行 + 扩展 | 同上 + 视角覆盖度评估 |

执行位置：进入 L1 之前。
输出位置：研究报告第一部分（## P0: 研究视角），供后续 L1-L5 参照。

## 默认法律视角模板

每个法律问题至少从以下视角审视。按案件类型自动裁剪。

### 通用视角（所有法律问题）

| 编号 | 视角角色 | 核心关切 | 典型查询模式 |
|------|---------|---------|------------|
| P0 | **法律规范分析者** | 法条文义/体系/目的、规范冲突与竞合 | 法条原文 + 立法解释 + 学理通说 |
| P1 | **原告/申请人** | 最大化主张、最有利解释、举证策略 | 支持性判例 + 有利口径 + 赔偿计算 |
| P2 | **被告/被申请人** | 有效抗辩、缩小/免除责任、程序拖延 | 抗辩路径 + 驳回判例 + 时效/管辖异议 |
| P3 | **裁判者/法院** | 审级管辖、类案统一、社会效果、司法经济 | 指导案例 + 裁判规则 + 各院口径差异 |
| P4 | **监管/政策** | 合规要求、公共利益、行业秩序、行政后果 | 部门规章 + 政策文件 + 行政处罚 |
| P5 | **实务操作** | 执行可行性、时间/成本、协商空间、替代方案 | 执行判例 + 保全策略 + 调解/仲裁 |

### 合同纠纷增补

| 编号 | 视角 | 核心关切 |
|------|------|---------|
| P6 | 合同起草者 | 条款目的、交易背景、行业惯例、默示条款 |

### 侵权纠纷增补

| 编号 | 视角 | 核心关切 |
|------|------|---------|
| P7 | 受害人 | 损害范围、因果关系证明、精神损害赔偿、惩罚性赔偿 |

### 公司/商事增补

| 编号 | 视角 | 核心关切 |
|------|------|---------|
| P8 | 小股东 | 知情权、利润分配、退出/回购、代表诉讼 |
| P9 | 债权人 | 偿债能力、担保效力、法人人格否认、追索路径 |

### 行政诉讼增补

| 编号 | 视角 | 核心关切 |
|------|------|---------|
| P10 | 行政相对人 | 程序合法性、事实认定错误、比例原则 |
| P11 | 行政机关 | 职权依据、公共利益、程序合规 |

## 视角驱动检索（P0 输出 → L2/L3 输入）

P0 不是装饰性的前置步骤——它的产出直接注入后续检索的具体 query。

### 视角 → 查询生成规则

```
每个视角 p 生成 2-3 个定向查询：

1. 法规查询（→ L2）:
   "[核心法条关键词] [视角立场词] [地域限定（如有）]"

2. 案例查询（→ L3）:
   "[争议焦点关键词] [视角结果词] 判例 [层级限定]"

3. 政策/实务查询（→ L2/L3 补充）:
   "[行业/领域] [视角关切词] [最新/规定/口径]"
```

### 视角立场词映射

| 视角 | 己方查询词（找有利素材） | 对方查询词（反方论证素材） |
|------|------------------------|-------------------------|
| P1 原告 | 支持 保护 确认 赔偿 胜诉 | 驳回 不支持 证据不足 败诉 |
| P2 被告 | 抗辩 免责 不构成 时效 驳回 | 认定 承担责任 赔偿 支持 |
| P3 法院 | 裁判规则 统一适用 指导案例 会议纪要 | — |

### 实际示例

```
用户问题：建设工程价款优先受偿权行使期限

P0 发现视角后 → 生成以下分视角查询：

P1（承包人/原告）:
  - 「建设工程价款优先受偿权 行使期限 起算点 有利解释」
  - 「建设工程价款优先受偿权 18个月 催告 中断」
  - 「建设工程价款优先受偿权 放弃 无效 判例 支持」

P2（发包人/被告）:
  - 「建设工程价款优先受偿权 超期 驳回 判例」
  - 「建设工程价款优先受偿权 起算点 未竣工 应付之日」
  - 「建设工程价款优先受偿权 发包人 抗辩 成功」

P3（法院视角）:
  - 「建设工程价款优先受偿权 与消费者物权期待权 冲突 顺位」
  - 「建设工程价款优先受偿权 指导案例 裁判规则」

P4（监管视角）:
  - 「建设工程价款 竣工备案 验收 合规 要求」

→ 这些查询分别注入 L2 法规检索和 L3 案例检索
→ 检索结果自然覆盖多方视角，而非仅承包人一方的信息
```

## 视角冲突处理

当 P1 和 P2 视角的检索结果明显矛盾时，这不是 bug——这正是案件的核心争议所在：
- **不试图调和**：矛盾信息保留并标注为争议焦点
- **按来源层级标注**：最高法观点 vs 地方法院口径 → 标注效力层级
- **P3 视角（法院）的检索结果通常具有更高的决策参考价值**

## Gotchas

1. **视角不是越多越好**：默认 5-6 个（P0-P5），具体案件按需增补。视角太多导致检索发散、上下文溢出。
2. **P0 是工具不是目的**：视角发现是为了生成更好的查询，不是为了写漂亮的视角矩阵。如果视角识别消耗过多 token 但查询质量没有提升，简化。
3. **裁判者视角最容易被忽略**：律师天然倾向当事人视角，但法院关注点（审级、管辖、类案统一、社会效果、执行难易）往往决定案件走向。这个视角不能省。
4. **用户语气判断优先级**：user 有明显立场偏向（如「我方」「对方违约」）→ P1/P2 视角标注 🔴 重点但 P2 仍执行；user 语气中性（「研究一下XX」）→ 所有视角等权。
5. **视角冲突是价值所在**：不要因为检索结果矛盾就试图选一个「正确」答案——标注冲突来源和层级，供用户自行判断。
